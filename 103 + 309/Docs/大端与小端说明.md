# 大端与小端说明

## 1. 概念

大端序（Big-Endian）和小端序（Little-Endian）描述的是**多字节数据在内存中的存放顺序**。

- 大端序：高字节放在低地址，低字节放在高地址。
- 小端序：低字节放在低地址，高字节放在高地址。

这里说的是“字节顺序”，不是“位顺序”。

## 2. 例子

以 `0x12345678` 这个 `uint32_t` 为例，假设起始地址是 `0x1000`：

### 大端序

| 地址 | 内容 |
|---|---|
| `0x1000` | `0x12` |
| `0x1001` | `0x34` |
| `0x1002` | `0x56` |
| `0x1003` | `0x78` |

### 小端序

| 地址 | 内容 |
|---|---|
| `0x1000` | `0x78` |
| `0x1001` | `0x56` |
| `0x1002` | `0x34` |
| `0x1003` | `0x12` |

对于 `uint16_t value = 0x1234`：

- 大端发送：`12 34`
- 小端发送：`34 12`

## 3. 为什么会出问题

很多 MCU 默认是小端架构。  
如果直接写：

```c
memcpy(&data[0], &value, 2);
```

那么 `data[0]` 和 `data[1]` 的顺序通常会跟本机内存一致。  
在小端平台上，这会把低字节先发出去。

这在以下场景里最容易出错：

- CAN 报文
- UART 协议
- Modbus/TCP 或自定义网络协议
- 与 PLC、上位机、网关、其他 MCU 通信

## 4. 使用场景

### 4.1 大端更常见的场景

- 网络协议：通常按“大端”传输，也叫 network byte order
- 传感器/协议帧：协议手册明确规定高字节在前
- 上位机、网关、PLC 通信：很多协议天然规定固定字节序

### 4.2 小端更常见的场景

- MCU 内部变量存储
- x86/ARM 本地处理
- 某些私有协议明确规定低字节在前

### 4.3 结论

**内存里的字节序** 和 **线上协议的字节序** 不一定相同。  
写协议时应该优先遵守协议定义，而不是直接依赖本机内存布局。

## 5. CAN 发送里的典型问题

在 CAN 报文中，很多协议会明确要求：

- 16 位数值：高字节在前
- 32 位数值：最高字节在前
- 单字节字段：无字节序问题

如果直接 `memcpy` 多字节变量，就会出现：

- 接收端读到的数值偏大或偏小
- 版本号、容量、电压、电流全都不对
- 调试时看到报文字节“对不上协议表”

## 6. 本项目中的例子

在 `Can_HDX.c` 中，`feidao_can_send` 相关数据已经改成显式大端打包。

### 6.1 电压/电流帧

例如：

- 电压：`uint32_t voltage`
- 电流：`int32_t current`

发送时按大端写入：

- `data[0]` 放最高字节
- `data[3]` 或 `data[7]` 放最低字节

### 6.2 容量帧

`real_cap`、`design_cap` 这类 `uint32_t` 字段也按大端发送。

### 6.3 SOC / SOH / 状态帧

这类报文中有 `uint16_t` 字段，例如：

- 剩余充电时间
- 循环次数
- 软件版本
- 容量信息

都改成了高字节在前。

## 7. 如何手动判断字节序

对于 `0xABCD`：

- 如果报文里先看到 `AB`，再看到 `CD`，就是大端
- 如果报文里先看到 `CD`，再看到 `AB`，就是小端

对于 `0x12345678`：

- 大端：`12 34 56 78`
- 小端：`78 56 34 12`

## 8. 如何避免再次出错

- 不要用 `memcpy` 直接拷贝多字节标量到协议缓冲区
- 对协议字段写专门的打包函数，例如 `put_u16_be`、`put_u32_be`
- 接收端也要按协议定义解包，不要默认按本机字节序处理
- 如果协议文档里没有写清楚字节序，应该补充说明

## 9. 工程建议

- 内存数据结构可以继续保持本机习惯
- 只在“协议边界”进行字节序转换
- 发送和接收都尽量封装成统一工具函数
- 对重要报文增加抓包验证，确认字节顺序一致

## 10. 一句话总结

大端和小端的本质区别，就是多字节数据“谁先发、谁先存”的顺序不同。  
**协议怎么规定，就怎么打包，不要直接依赖本机内存布局。**
