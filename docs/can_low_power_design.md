# CAN 低功耗与错误处理优化说明

## 背景

当前主循环实际运行的是 `App_BmsEUavcan()` 周期广播，旧的 `App_Can()` 标准帧应答任务暂未打开。原 CAN 初始化保持 `CAN_NART = DISABLE`，当总线上没有其他节点应答 ACK 时，bxCAN 会持续自动重发，容易带来额外功耗、邮箱长期占用以及错误计数累积。

本次优化目标是在不改变现有 EUAVCAN 报文内容、周期和标准帧应答接口的前提下，降低无 ACK 场景下的发送功耗，并统一 CAN 发送结果处理。

## 策略

1. `CAN_NART = ENABLE`
   - 含义是启用 No Automatic Retransmission，即关闭硬件自动重发。
   - 无 ACK 时单帧失败后释放邮箱，避免硬件持续重发。
   - 可靠性由软件层按报文类型决定是否重试。

2. 统一发送入口
   - 新增 `Can_HDX_Transmit()`：提交 CAN 帧并轮询 `CAN_TransmitStatus()`，返回 `OK / BUSY / FAILED / BUS_OFF`。
   - 新增 `Can_HDX_TransmitRetry()`：给旧标准帧应答和测试帧保留少量软件重试，避免 NART 改动后降低应答可靠性。
   - 当前工程内直接调用 `CAN_Transmit()` 的位置收敛到 `Can_HDX.c`。

3. EUAVCAN 广播退避
   - 保持正常在线时 `250ms` 启动一轮、每轮 `10` 帧的现有广播节奏。
   - 单帧发送成功后才推进 `frameIndex`，保证多帧传输顺序不变。
   - 连续 `3` 次发送失败后进入 `1s` 无 ACK 退避，退避结束后自动探测恢复。
   - 检测到 BusOff 时进入 `5s` 退避，并继续复用原有 BusOff 恢复监控。

4. 收发器供电
   - 本次没有在运行态关闭 `GPIO_CMNT_EN`。
   - 原因是关闭收发器会影响外部节点主动帧接收，需要结合 `GPIO_INT_WK_CMNT` 唤醒时序和硬件实测后再启用。
   - 现阶段优先降低无 ACK 自动重发和软件高频重试带来的动态功耗。

## 验证要点

1. 接 CAN 设备：
   - EUAVCAN 报文仍按既有周期完整发出。
   - 多帧尾字节、transfer-id 和 CRC 不变。
   - 标准帧请求应答仍能返回对应数据帧。

2. 不接 CAN 设备：
   - 邮箱不应长期被占满。
   - 无 ACK 后不再持续硬件自动重发。
   - 连续失败后进入约 `1s` 探测周期，功耗应低于原持续重发状态。

3. 异常恢复：
   - BusOff 后仍能按原恢复流程尝试恢复。
   - 重新接入 CAN 设备后，最迟在下一次探测周期恢复广播。
