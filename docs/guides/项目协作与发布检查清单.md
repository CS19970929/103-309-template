# 项目协作与发布检查清单

本文是当前 `103-309-template` 仓库的长期协作入口，用于把 AI 协作、日常开发、测试隔离、安全烧录、发布检查和文档沉淀收口到同一套规则里。

目标不是替代已有文档，而是给每次修改前后提供一张可执行检查表。具体工具入口见 [BMS 日常开发工作流](BMS_DAILY_DEV_WORKFLOW.md)，自动检查细节见 [项目自动化检查与发布流程](项目自动化检查与发布流程.md)。

## 1. 协作角色分工

### 1.1 人负责的边界

- 明确本次任务属于量产修复、功能开发、架构重构、测试验证、文档审计还是工具建设。
- 确认硬件现场条件，例如板卡型号、串口号、CAN 适配器、ST-Link、供电方式、负载状态。
- 对涉及烧录、量产配置、客户协议、出货版本号的最终决策负责。
- 在需要接板验证时提供实际现象、日志、截图或串口/CAN 抓包。

### 1.2 AI 负责的边界

- 先读仓库文档、工程配置、源码入口和现有脚本，再给出判断或修改。
- 对较大任务先拆分模块边界、影响范围、风险点和验证方式。
- 修改代码时同步更新必要文档和检查脚本，避免规则只停留在对话里。
- 默认白名单提交目标文件，不把无关未跟踪文件带入提交。
- 对不能本机验证的硬件行为明确标注“未接板验证”，并给出后续板端确认步骤。

## 2. 任务类型与默认流程

| 任务类型 | 默认流程 | 交付物 |
| --- | --- | --- |
| 量产修复 | 先定位入口和影响链路，再小步修改，最后严格检查 | 代码修改、验证记录、必要说明文档 |
| SOC 调参/重构 | 先核对 `SOC.c` / `SocEnhance.c` / AFE 输入 / Flash 快照，再改算法 | SOC 说明、host 测试、在线验证步骤 |
| 低功耗/RTC/CAN | 先画清进入休眠、唤醒、CAN 发送、GPIO 电源脚恢复链路 | 链路说明、风险点、板端验证清单 |
| 通信协议/上位机 | 先对照地址索引、协议文档和现有脚本，再修改收发逻辑 | 协议说明、脚本入口、回归样例 |
| Flash/EEPROM/参数 | 先确认地址、页大小、双槽/日志策略和掉电恢复边界 | 存储布局说明、读写校验、回退方案 |
| 工具/自动化 | 优先扩展 `tools/` 固定入口，避免临时命令散落 | 脚本、README 入口、使用示例 |
| 文档审计 | 先做源码和文档 inventory，再按模块输出结论 | 中文审计文档、README 索引 |

## 3. 修改前检查

每次开始修改前先确认：

- `git status --short --branch`，识别当前分支和未提交内容。
- 阅读 `AGENTS.md`、`README.md` 和本任务相关专题文档。
- 明确不能碰的边界：IAP 地址、App 地址、量产配置、通信地址、Flash 布局、客户兼容协议。
- 如果涉及 Keil/C 文件，确认是否需要保持 GBK/ANSI 编码，特别是 `Project_Config.h`。
- 如果工作区存在无关文件，默认只对白名单文件修改和提交。

## 4. 开发中检查

### 4.1 代码修改原则

- 优先沿用现有模块边界，不把 SOC、通信、低功耗、存储逻辑混在一次大改里。
- 新增测试/调试模式必须有明确隔离入口，例如独立 Keil target、固定脚本入口、`tools/project_check.py` 检查或 `Project_BuildGuard.h` 范围约束；不要重新把临时测试宏塞回量产配置主视图。
- 新增危险操作必须同步更新 `tools/project_check.py` 或固定脚本入口。
- 涉及协议地址、Flash 地址、烧录地址的规则必须写入文档或脚本，不依赖对话记忆。

### 4.2 文档同步原则

- 较大代码变更必须补充说明文档，至少写清楚需求、现状逻辑、修改点、风险、验证方式。
- 长期有效文档放在根目录 Markdown，并接入 `README.md` 索引。
- 临时待办放入 `TODO.md` 或 `TEST_PENDING.md`，验证完成后再沉淀为正式文档。

## 6. 烧录安全检查

### 6.1 固定地址

| 区域 | 地址 | 规则 |
| --- | --- | --- |
| IAP / Bootloader | `0x08000000` | 禁止被 App bin 覆盖 |
| 正常 App | `0x08004800` | App 烧录唯一允许起始地址 |
| App scatter | `103 + 309/Project/Users/Objects/FD_Release.sct` | 必须与 App 地址保持一致 |

### 6.2 唯一推荐 App 烧录入口

```powershell
.\tools\soc_flash_app_safe.ps1 -Bin "103 + 309\Project\Users\Objects\FD_Release.bin" -Flash
```

禁止把 `FD_Debug.bin` 或 `FD_Release.bin` 裸写到 `0x08000000`。

修改或新增烧录脚本时必须保留：

- `0x08004800` 地址检查。
- dry-run 输出。
- 对 `0x08000000` 裸写 App bin 的阻断。

## 7. SOC 测试模式隔离

当前量产源码未启用 `PROJECT_CFG_SOC_TEST_MODE_ENABLE` / `PROJECT_CFG_SOC_TEST_ACCEL_TICKS_MAX` 注入式 SOC 测试入口，这两个宏不再作为当前 `Project_Config.h` 配置项。

测试结束后必须恢复量产配置，并通过 `COM4/19200/slave=1` 读取：

- `0xD000`：确认主状态区运行正常。
- `0xD300`：确认测试入口状态或兼容占位。

量产固件读到 `0xD300 supported=0` 是正常结果，表示 MCU 注入式 SOC 测试入口已关闭。

## 8. SOC 测试上位机启动

不要直接双击：

```text
tools\soc_test_ui.py
```

固定启动方式：

```powershell
.\tools\start_soc_test_ui.ps1
```

自动演示启动方式：

```powershell
.\tools\start_soc_test_ui.ps1 -Demo -Port COM4 -Baud 19200 -Slave 1 -Samples 10 -Interval 0.5
```

当前机器推荐使用已验证的 `py -3.9`。如果报 `No module named 'serial'`，先确认：

```powershell
py -3.9 -c "import serial"
```

如果串口打开失败，先排查 COM 口占用，再排查 Python 环境。

## 9. 发布前检查清单

发布前逐项确认：

- Keil Target 为 `FD_Release`。
- `FD_Release` 不定义 `_DEBUG_`、`PROJECT_CFG_DEBUG_WATCH_ENABLE`、`ELOG_OUTPUT_ENABLE`、`FLASH64K_APP_*` 等调试/测试符号。
- `FD_Release` 不把 `PROJECT_CFG_BUILD_PROFILE` 覆盖成非 0。
- SOC 测试模式关闭。
- 看门狗、发布保护、日志输出符合量产要求。
- `tools/project_check.py` 通过。
- `git diff --check` 通过。
- Release 构建成功。
- App bin 只通过 `soc_flash_app_safe.ps1` 烧录到 `0x08004800`。
- 板端读取 `0xD000` 正常。
- 板端读取 `0xD300 supported=0`。
- README 和相关专题文档已经同步。
- `git status --short` 中只包含本次应提交文件。

## 10. Git 提交流程

默认流程：

```sh
git status --short --branch
python3 tools/project_check.py
git diff --check
git add <本次目标文件>
git commit -m "<清晰描述本次修改>"
```

提交原则：

- 默认白名单 `git add`，不使用 `git add -A`，除非明确要提交当前目录全部修改。
- 提交前确认无关未跟踪文件没有被带入。
- 提交信息应说明修改目标，例如 `Document collaboration and release checklist`。
- 如果只是分析或审计，不需要强行提交；如果已经修改仓库文件，应在最终说明中列出修改和验证结果。

## 11. AI 交接材料

需要 AI 继续定位问题时，优先提供小而完整的现场：

- `git status --short --branch`
- 最近一次失败命令和完整错误输出
- `tools/project_check.py` 输出
- 串口/CAN/Modbus 关键日志
- 板端状态：供电、负载、串口号、波特率、slave 地址
- 本次目标：只分析、只出文档、改代码、烧录验证、还是提交

如果已经运行长期监控，可先生成 AI 日志包：

```powershell
.\tools\bms_collect_ai_logs.ps1
```

## 12. 长期资产建设路线

优先把以下能力沉淀成脚本、文档或 skill：

1. BMS 项目总检查脚本：覆盖地址、宏、Keil Target、Flash 布局和危险测试项。
2. SOC 验证套件：覆盖骑行、充电、静置、低压、大电流压降、休眠恢复、满电到 100、低压到 0。
3. 通信协议索引：统一 `0xD000`、`0xD300`、`0xC000`、参数写入地址、CAN 帧和 Modbus 命令。
4. 低功耗审计模板：固定检查 RTC、EXTI、GPIO 电平、CAN 唤醒、MOS、LED、Flash 保存和唤醒恢复顺序。
5. Flash/EEPROM 布局检查器：自动核对 App 地址、后 64K、SOC/AFE/RW_PARAM/LOG 双槽地址、页大小和 C8/CB 风险。
6. AGENTS + skill 模板库：把中文输出、先审计、白名单提交、量产隔离、官方资料引用等要求固化。
