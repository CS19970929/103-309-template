# CAN 通讯常见错误、异常原因和解决办法

文档状态：CURRENT
源码验证：PARTIAL
主要参考源码：`103 + 309/Project/Source/Can_HDX.c`, `103 + 309/Project/Source/RTC.c`, `103 + 309/Project/Source/conf/conf_gpio.h`, `docs/protocol/can_protocol.md`
最后更新时间：2026-06-02

## 1. 当前项目 CAN 边界

当前 BMS App 的 CAN 关键策略：

- 使用 STM32F103 bxCAN，CAN1，PA11/PA12。
- 当前位时序：`SJW=1tq`, `BS1=5tq`, `BS2=2tq`, `Prescaler=4`，文档口径为 `250 kbit/s`。
- `CAN_ABOM = ENABLE`：bus-off 交给 bxCAN 自动恢复。
- `CAN_NART = ENABLE`：关闭硬件自动重发，无 ACK 时快速失败，避免无对端持续重发增加功耗。
- `GPIO_CMNT_EN/PIN_CMNT_EN = PB4` 控制 CAN 收发器电源，`Bit_RESET` 为上电，`Bit_SET` 为断电。
- 运行态 `InitCan()` 打开 CMNT；`Can_PrepareSleep()` 睡前关闭 CMNT；RTC STOP 周期唤醒不主动广播 CAN，真正唤醒恢复后再通信。
- 飞道周期广播扩展帧基址为 `0x14F80200 + chd_index`。
- CAN App 标准帧命令为 `0x60`，ACK 为 `0x61`，当前不允许随意修改 ID、payload 和命令含义。

## 2. 快速排查顺序

现场排查先从物理层到应用层，不要一开始就改代码：

1. 确认供电：BMS、CAN 收发器、USB-CAN 适配器和对端设备都已供电。
2. 确认 `CMNT_EN`：运行态应为 CAN 上电电平，RTC STOP 前应关闭，唤醒恢复后应打开。
3. 确认接线：CANH/CANL 未接反，GND 参考可靠。
4. 确认终端电阻：总线两端各 120Ω，断电测 CANH-CANL 约 60Ω。
5. 确认波特率和采样点：本项目按 250 kbit/s 排查。
6. 确认帧格式：飞道周期帧是扩展帧；CAN App 命令是标准帧。
7. 看错误寄存器：优先看 `CAN1->ESR` 的 BOFF、EPVF、EWGF、LEC。
8. 看协议响应：周期广播、`0x60/0x61` ACK、`READ_BLOCK` 多帧顺序。
9. 再判断是否是低功耗、队列、权限或上位机解析问题。

## 3. 常见现象、原因和解决办法

| 现象 | 常见原因 | 定位方法 | 解决办法 |
|---|---|---|---|
| 完全收不到任何帧 | 收发器未上电、CANH/CANL 断线、波特率不一致、适配器未打开、过滤器/帧格式错误 | 测 `CMNT_EN`，示波器看 CANH/CANL，USB-CAN 监听全部帧，确认 250 kbit/s | 先恢复收发器供电和接线；统一波特率；监听全部扩展帧和标准帧 |
| 能看到发送动作但无 ACK | 总线上只有一个节点、对端未上电、对端波特率不同、CANH/CANL 接反、终端错误 | 看 `CAN_TransmitStatus` 失败、`CAN1->ESR`、示波器 ACK bit | 接入至少一个正常节点；修正波特率/接线/终端；确认对端不在 silent/listen-only |
| 周期帧不发或间隔异常 | 主循环未跑 `App_Can()`、CAN busy、系统进入低功耗、TIM3 tick 异常、物理层无 ACK | 看主循环心跳、`g_dbg.can.tx_queue/power_on/bus_off/esr`、抓 `0x14F80200+index` | 先确认主循环和 10ms tick；排除物理层 ACK/BOFF；确认没有进入 RTC STOP |
| `0x60` 命令无 `0x61` ACK | 发错标准帧 ID、DLC 不是 8、magic/CRC 错、目标 `can_addr` 错、BMS 正在低功耗或串口占用寄存器缓存 | 抓标准帧，检查 `A5 5A`、CRC16、`CAN_ADRESS_STD_ID` 偏移；看串口是否 busy | 按协议重发标准帧；修正 CRC 和节点地址；唤醒 BMS 后再发；避免串口和 CAN 同时大量读写 |
| `READ_BLOCK` 丢帧或顺序错 | 上位机接收缓存不够、总线负载高、BMS TX queue 堆积、低功耗切入 | 抓 `0x86` 数据帧序号，观察 `tx_queue` 和 sleep block | 降低请求频率；读块期间禁止进入 STOP；上位机按序号重组并设置超时重试 |
| bus-off | 长时间错误发送、短路、波特率错误、终端严重错误、强干扰、收发器异常 | 看 `CAN1->ESR & CAN_ESR_BOFF`，示波器看差分波形 | 修复物理层问题；恢复总线后依赖 `CAN_ABOM` 自动恢复；恢复后确认周期帧继续发送 |
| 短时间能通信，随后断开 | 接触不良、终端松动、共地不好、收发器过热/欠压、低功耗关闭 CMNT | 摇线测试、热风/冷喷、测收发器 VCC 和 `CMNT_EN`，看进入 STOP 时序 | 固定线束和端子；补可靠地线；确认低功耗策略是否符合现场需求 |
| 只收得到扩展帧，收不到 App ACK | 上位机只监听扩展帧或过滤器过滤标准帧 | USB-CAN 关闭过滤，分别监听标准帧和扩展帧 | 上位机同时打开标准帧 `0x61` 和扩展帧 `0x14F802xx` |
| 只收得到 App ACK，收不到周期帧 | 扩展帧过滤错误、周期调度未运行、低功耗、总线错误 | 抓全部扩展帧，看 `App_Can()` 是否运行 | 修正过滤器；确认运行态未睡眠；修复 ACK/总线问题 |
| 数据看起来乱或数值不对 | 字节序、倍率、offset、符号位、单位理解错；协议版本字段固定或未确认 | 对照 `CanFeidaoFrames.c` 逐字节解析，抓原始 8 bytes | 不先改 CAN 驱动；先统一协议表、单位、字节序和上位机解析 |
| IAP 进入失败 | `ENTER_IAP` guard 错、节点地址错、ACK 还没发完就复位、BMS 未运行 App、Bootloader/节点不匹配 | 抓 `0x60/0x61`，确认 `0xC3 0x3C can_addr`，确认复位后 IAP 帧 | 按 App CAN 地址选中目标；确保 ACK 后延迟复位；多设备时保证 IAP 节点唯一 |
| 多设备总线响应混乱 | 多个 BMS 使用相同 App CAN 地址或 IAP 节点 | 抓响应 ID 和数据，看是否多个设备同时 ACK | 量产/测试前分配唯一地址；进入 IAP 前只让目标板进入 |
| 上位机提示超时但总线上有帧 | 上位机过滤、帧类型、时间戳、超时窗口或解析线程问题 | 用第二个监听工具旁路抓包，对比上位机日志 | 先证明总线是否有正确 ACK；再修上位机过滤和超时参数 |
| 休眠后 CAN 不通 | RTC STOP 中 CMNT 已关闭，当前策略不在周期唤醒中广播 CAN | 测 `CMNT_EN`，确认是否仍在 STOP loop；看唤醒源 | 通过外部唤醒退出低功耗后再通信；确认唤醒恢复调用 `InitCan()` |

## 4. 错误状态含义

| 状态 | 含义 | 常见原因 | 处理原则 |
|---|---|---|---|
| Error Active | 正常错误状态，可继续主动发送错误帧 | 偶发干扰、单次 ACK 问题 | 记录并继续观察，不必立即复位 |
| Error Warning | 错误计数超过 warning 阈值 | 物理层不稳定、波特率边缘、接触不良 | 重点查线束、终端、电源、波形 |
| Error Passive | 错误计数较高，节点错误行为受限 | 长时间通信异常 | 不要只清标志，必须查物理层或位时序 |
| Bus-off | 控制器退出总线，避免继续干扰网络 | 严重短路、错误波特率、无效 ACK、强干扰 | 先修总线；本项目由 `CAN_ABOM` 自动恢复 |
| Stuff/Form/CRC/Bit Error | CAN 帧物理或位级错误 | 干扰、采样点不合适、线束过长、终端不良 | 用示波器看差分波形，必要时调整位时序 |
| ACK Error | 发送节点没有收到 ACK | 无对端、对端未上电、对端 silent、波特率不一致 | 接入正常对端，确认对端确实参与 ACK |

## 5. 物理层检查清单

| 检查项 | 正常预期 | 异常处理 |
|---|---|---|
| CANH-CANL 终端电阻 | 断电测约 60Ω | 120Ω 表示只接了一端；无穷大表示无终端；过低表示终端过多或短路 |
| CANH/CANL 电压 | 空闲时差分接近 0V，通信 dominant 有明显差分 | 无波形先查供电/使能；波形畸变查终端和线长 |
| 收发器 VCC | 满足收发器规格 | 欠压会导致间歇通信、错误计数升高 |
| GND 参考 | BMS 与工具/对端有可靠参考 | 共地差会导致共模超限，表现为间歇错误 |
| 线束 | 双绞线、短支线、端子牢靠 | 支线过长、接触不良会导致反射和偶发错误 |
| CANH/CANL 极性 | 未接反 | 接反通常完全不通或大量错误 |

## 6. 软件层检查清单

| 检查项 | 当前项目预期 | 异常处理 |
|---|---|---|
| 波特率 | `250 kbit/s` | 上位机、USB-CAN、对端设备统一配置 |
| 帧类型 | 周期帧为扩展帧，App 命令为标准帧 | 上位机过滤必须同时覆盖标准帧和扩展帧 |
| App 命令 ID | 请求 `0x60`，ACK `0x61`，叠加 `CAN_ADRESS_STD_ID << 7` | 多设备时确认地址偏移 |
| CRC | `Sci_CRC16RTU(data, 6)` 写入 data[6..7] | ACK 不回时先校验 magic 和 CRC |
| TX queue | 软件队列 32 帧 | 高负载或块读时降低请求频率 |
| 无 ACK | `CAN_NART=ENABLE` 下失败会较快暴露，软件不再维护 no-ACK 退避计数 | 不要误判为软件没发，先确认是否有对端 ACK |
| bus-off | `CAN_ABOM=ENABLE` 自动恢复 | 修复物理层后等待恢复，不要反复 reset 掩盖问题 |
| 低功耗 | RTC STOP 中关闭 CMNT，不主动广播 CAN | 需要通信时先唤醒，再验证 `InitCan()` 恢复 |

## 7. 典型排查路径

### 7.1 完全不通

1. 断电测 CANH-CANL 电阻。
2. 上电测收发器 VCC 和 `CMNT_EN`。
3. USB-CAN 设置 250 kbit/s，关闭过滤监听全部帧。
4. 若无波形，查供电、使能、MCU 是否运行。
5. 若有波形但工具不显示，查波特率、帧类型和适配器驱动。

### 7.2 有发送但没有 ACK

1. 确认总线上至少有一个正常对端。
2. 确认对端不是 listen-only/silent 模式。
3. 确认波特率和采样点一致。
4. 看 ACK bit 和 `CAN1->ESR`。
5. 修复后观察 `tx_queue` 是否释放、周期帧是否恢复。

### 7.3 bus-off

1. 不先改代码，先断开总线确认本机是否恢复。
2. 检查短路、接反、终端、电源和波特率。
3. 恢复物理层后等待 `CAN_ABOM` 自动恢复。
4. 抓运行态周期帧，确认 `0x14F80200+index` 继续发送。
5. 若反复 bus-off，重点查干扰、线束、终端和收发器。

### 7.4 低功耗后不通信

1. 判断设备是否仍在 RTC STOP loop。
2. 测 `GPIO_CMNT_EN`：睡前关闭是当前预期。
3. 触发外部唤醒或退出低功耗。
4. 确认 `InitRunAfterStopWakeup()` 后 `InitCan()` 打开 CMNT。
5. 再抓周期帧和 App ACK。

## 9. 处理原则

- 先物理层，后协议层，最后才改固件。
- 先抓原始 CAN 帧，再判断上位机显示是否正确。
- bus-off 和无 ACK 多数不是算法问题，优先查总线、波特率、终端、对端供电。
- 低功耗问题必须同时看 `CMNT_EN`、唤醒源和 `InitCan()` 恢复路径。
- 不要为了“临时能通”随意修改 CAN ID、payload、寄存器地址或 IAP 节点。
