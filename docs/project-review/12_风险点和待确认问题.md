# 12 — 风险点和待确认问题

## 安全相关风险（高优先级）

### S1: SW OVP 阈值与 AFE 配置脱钩

| 项目 | 详情 |
|------|------|
| **位置** | `DataDeal.c:1135-1153` (`new_todo_logi()`) |
| **问题** | MCU 软件 OVP 检测使用硬编码 `4280mV`，不读取 `AFE_Parameters_RS485_Struction.u16VcellOvp.curValue` |
| **影响** | 用户通过 RS485 修改 OVP 阈值后，SW OVP 仍在 4280mV 触发，保护点不一致 |
| **严重程度** | ⚠️ 高 — 对于 LiFePO4 电池 (OVP=3650mV)，SW 保护在 AFE 硬件保护之后才触发 |
| **验证方法** | 通过 RS485 将 OVP 改为 3650mV，确认 SW OVP 是否仍在 4280mV 触发 |

### S2: 化学体系阈值分散在 4 个文件中

| 项目 | 详情 |
|------|------|
| **位置** | `Fault.h`, `SH367309_Func.h`, `SH367309_DataDeal.h`, `DataDeal.h` |
| **问题** | 三元锂 vs 磷酸铁锂的阈值定义在 4 个文件中各自用 `#ifdef TERNARYLI` 维护 |
| **影响** | 修改化学体系阈值时极易遗漏某处，导致保护阈值不一致 |
| **严重程度** | ⚠️ 高 |
| **验证方法** | 对比 4 个文件中相同故障类型的阈值，确认完全一致 |

### S3: HICCUP 休眠阻塞主循环

| 项目 | 详情 |
|------|------|
| **位置** | `rtc_sleep.c:285-287` |
| **问题** | HICCUP 模式使用 `while(rtc_sleep_run_hiccup_cycle())` 阻塞在主循环中 |
| **影响** | 休眠期间 CAN 帧不响应、RS485 无回复、看门狗不喂、Flash 不写入。如果每次唤醒后 CAN 需要发送帧，会丢失通信窗口 |
| **严重程度** | ⚠️ 中 — 功能退化但不影响安全 |
| **验证方法** | 在 HICCUP 休眠期间通过 CAN 发送应用指令，确认是否响应 |

### S4: 均衡电压硬编码 4160mV

| 项目 | 详情 |
|------|------|
| **位置** | `SH367309_DataDeal.c:75` |
| **问题** | `temp = (4160 + 10) / 20;` — 均衡开启电压固定为 4160mV |
| **影响** | `OtherElement.u16Balance_OpenVoltage` 的配置值被忽略，RS485 修改无效 |
| **严重程度** | ⚠️ 中 — 功能 Bug |
| **验证方法** | 通过 RS485 修改均衡电压为 4000mV，读回确认 AFE 寄存器是否改变 |

### S5: SW OVP 阈值在认证模式下触发熔断

| 项目 | 详情 |
|------|------|
| **位置** | `DataDeal.c:1097-1121` (`_UL_RENZHENG_ENABLE_` 条件编译) |
| **问题** | 认证模式下，AFE 通信故障 + 高电压条件持续 5 秒，会触发 `GPIO_RF_EN = 1`（硬件熔断保险丝） |
| **影响** | 如果 AFE 通信因 I2C 干扰误报 PEC 错误，可能导致误熔断 |
| **严重程度** | ⚠️ 高 — 硬件不可逆熔断 |
| **验证方法** | 确认 PEC 错误计数的阈值 (2 次) 是否合理，是否需要更长的确认时间 |

### S6: HardFault 后故障原因未利用

| 项目 | 详情 |
|------|------|
| **位置** | `stm32f10x_it.c:95-105` (HardFault_Handler), `FaultSnapshot.h` |
| **问题** | HardFault 将原因码写入 `BKP_DR16` 后直接复位，但启动后未读取利用 |
| **影响** | 现场故障分析缺失关键信息 |
| **严重程度** | 🔵 中 — 影响可维护性 |
| **验证方法** | 检查启动序列中是否有读取 BKP_DR16 的逻辑 |

### S7: 休眠期间 AFE 保护仍依赖硬件

| 项目 | 详情 |
|------|------|
| **位置** | `rtc_sleep.c` (睡眠状态机), `I2C_AFE1.c` |
| **问题** | MCU 进入 STOP 后无法通过 I2C 读取 AFE 状态。保护完全依赖 AFE 硬件阈值 (MTP 寄存器配置) |
| **影响** | 如果 AFE 硬件保护阈值配置错误，休眠期间无 MCU SW 保护兜底 |
| **严重程度** | ⚠️ 中 — 依赖 AFE 配置正确性 |
| **验证方法** | 确认 AFE MTP 寄存器在休眠前已完整写入正确的保护阈值 |

## 架构相关风险（中优先级）

### A1: Flash 存储无电源丢失恢复

| 项目 | 详情 |
|------|------|
| **位置** | `Flash.c` |
| **问题** | Flash 擦除期间掉电会导致该页面数据丢失。日志型存储有双页冗余，但双槽位存储写入时先擦除旧槽 |
| **影响** | 写入保护参数时断电 → 旧槽已擦除、新槽未完成 → 两个槽都可能无效 |
| **严重程度** | ⚠️ 中 — 低概率但高影响 |
| **验证方法** | 在 Flash 擦除过程中强制断电，重启后检查参数是否正确回退到默认值 |

### A2: `Fault_Flag_*` 与 `unMdlFault_*` 两套故障标志不一致

| 项目 | 详情 |
|------|------|
| **位置** | `Fault.h:382-384` (`Fault_Flag_*`) vs `Sci_Upper.h` (`unMdlFault_*`) |
| **问题** | `Fault_Flag_First/Second/Third` 仅被 RS485 清除命令清零，从未被任何保护逻辑设置。实际使用的故障标志是 `unMdlFault_Third` |
| **影响** | RS485 读取 `Fault_Flag_*` 始终返回 0（无意义），但读取 `g_stCellInfoReport.unMdlFault_*` 才是有效数据 |
| **严重程度** | 🔵 低 — 可能是历史遗留，需确认 RS485 上位机读取的是哪个地址 |
| **验证方法** | 触发一级过压故障，分别通过 RS485 读取 `Fault_Flag_First` 和 `unMdlFault_First` 的地址 |

### A3: `int64_t` 运算在 Cortex-M3 上极慢

| 项目 | 详情 |
|------|------|
| **位置** | `DataDeal.c:773` (电流校准), `SOC.c:34-38` (TypeC 等效电流) |
| **问题** | Cortex-M3 无 64 位硬件指令，`int64_t`/`uint64_t` 乘法和除法由软件仿真 |
| **影响** | 每次 200ms SOC 计算消耗 ~9000+ cycles 在 64 位运算上 (占 72MHz 的 <1%，但完全可避免) |
| **严重程度** | 🔵 低 — 不影响功能但浪费 CPU |
| **验证方法** | 用 uint32_t 重写后对比计算结果是否一致 |
