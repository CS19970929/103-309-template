# CAN 通信架构重构说明

日期：2026-05-21

## 需求梳理

当前 CAN 通信需要同时满足：

- 保留 1s 主动广播 `CAN_TX_0x02()`。
- 保留外部请求触发的 `0x00~0x11` 应答协议。
- 不强依赖 RX 中断，优先保证通信稳定。
- 不能再出现 CAN sleep 后 `Can_TransmitDeal()` 继续发送导致发送失败或请求标志被清掉的问题。
- CAN 收发器供电 GPIO 不在本次架构中控制，避免引入额外功耗和硬件状态不确定性。

## 当前实现策略

本次实现选择“普通运行期 CAN 常驻 Normal + 主循环轮询 FIFO”的稳定优先方案：

- `InitCan_CAN1()` 初始化后关闭 `CAN_IT_FMP0` 中断。
- `App_Can()` 每 10ms 调用一次时，先确保 CAN 处于 Normal 模式，再轮询接收 FIFO。
- 收到外部请求帧后，根据低 7 位请求 ID 映射到 `CanTxType_Flag` 对应应答标志。
- `Can_TransmitDeal()` 每次处理一个待发应答，按 `0x00 -> 0x11 -> Test` 顺序发送。
- 只有发送确认成功后才清除待发标志；无邮箱、无 ACK 或发送失败时保留标志，后续 10ms 周期继续重试。
- 1s 到点时独立发送 `CAN_TX_0x02()` 主动广播，并用发送结果更新 `sys_time.can_enable`。

这样外部请求不需要卡在广播后的短时间窗口内，只要系统处于普通运行状态，主循环轮询就可以接收和应答。

## 触发链路

### 主动广播

`App_Can()` 中的 `cnt_send_0x02` 每 10ms 增加一次，达到 `DELAYB10MS_1S` 后：

1. 清零计数。
2. 调用 `CAN_TX_0x02()`。
3. 根据返回值更新 `sys_time.can_enable`。

### 外部请求应答

外部主机发送标准帧请求后：

1. `App_Can()` 调用 `Can_PollReceive()`。
2. `Can_PollReceive()` 通过 `Can_DrainRxFifo()` 最多连续读取 8 帧。
3. `Can_ReceiveDeal()` 校验地址高位是否等于 `CAN_ADRESS_STD_ID`。
4. 请求 ID `0x00~0x11` 被转换为 `CanTxType_Flag` 位。
5. `Can_TransmitDeal()` 取出最小 ID 的待发标志并调用对应 `CAN_TX_0xXX()`。
6. `CAN_Tx_Data()` 等待硬件发送状态，成功后 `s_bLastCanTxOk = TRUE`。
7. `Can_TransmitDeal()` 仅在成功时清除该应答标志。

## 为什么不使用 RX 中断

此前打开 RX 中断后，存在一个关键竞争风险：

- 中断先读取 FIFO，只设置 `b1Can_Received`。
- 主循环再轮询 FIFO 时已经读不到该请求帧。
- 如果处理链路没有立即置应答标志，请求就可能丢失。

本次改为纯轮询后，FIFO 读取、请求解析、应答标志设置都在同一条主循环链路内完成，行为更可控，也更容易调试。

当前 ISR 仍保留兜底实现，但正常情况下 `CAN_IT_FMP0` 被关闭，不依赖中断收包。

## 关于 CAN sleep

如果普通运行期让 CAN 在两次 1s 广播之间 sleep，会带来两个问题：

- 外部请求在 sleep 期间无法稳定进入 FIFO。
- `Can_TransmitDeal()` 如果在 CAN 未恢复 Normal 时发送，会直接失败。

所以本次稳定优先版本不在 `App_Can()` 中反复执行 CAN sleep/wake。系统若后续需要进一步降功耗，应单独设计“低功耗模式”：

- 普通通信模式：CAN 常驻 Normal，保证请求随时响应。
- 低功耗模式：只能接受“主机在 1s 广播后窗口内请求”的约束，或增加外部唤醒硬件/EXTI。

这两个目标不能混在同一条无状态流程里，否则会在“省电”和“随时响应”之间互相破坏。

## 上板验证建议

- 接 USB-CAN，确认每 1s 可见 `0x02` 主动广播。
- 发送 `0x00~0x11` 请求，确认对应应答帧返回。
- 连续发送多个请求，确认不会因为一次发送失败就永久丢失待发标志。
- 断开 CAN 设备确认无 ACK 时不会阻塞主循环，待发标志会在后续周期继续重试。
- 确认普通运行期功耗变化；如果必须进一步降功耗，再单独切换到有明确接收窗口约束的低功耗 CAN 策略。
